# Requirements Document

## Introduction

The Weather_App shows a 5-day National Weather Service forecast for a city the user enters. This feature adds a short AI-generated plain-language summary of that 5-day forecast. The summary appears below the forecast after the forecast has rendered, and text streams into the page as the model produces it.

A browser page cannot call AWS Bedrock directly without exposing AWS credentials. The feature therefore adds a Summary_Service that holds the AWS permissions and calls Bedrock with the Converse Stream API. The Weather_App sends the forecast periods to the Summary_Service and displays the streamed text. The service must run beside the local server on localhost:8080 and must also fit the planned AWS deployment (private S3 behind CloudFront with a strict CSP, no backend today). Both constraints are covered below.

Constraints from project steering: plain HTML and JavaScript, no classes, interfaces, or caching, basic tests only (`node --check`), and no hardcoded city names.

## Glossary

- **Weather_App**: The browser application made of `index.html`, `weather.js`, and `styles.css`.
- **Forecast**: The list of up to 5 daytime periods returned by the National Weather Service and rendered by the Weather_App.
- **Summary**: A plain-language paragraph describing the Forecast, generated by the Model.
- **Summary_Panel**: The region of the page below the forecast table where the Summary is displayed.
- **Summary_Service**: A server-side endpoint at the path `/api/summary` on the same origin as the Weather_App. It receives the Forecast and returns the Summary as a stream of text.
- **Model**: The Amazon Bedrock foundation model that the Summary_Service invokes.
- **Converse_Stream_API**: The AWS Bedrock Runtime ConverseStream operation.
- **Unit_Toggle**: The existing button that switches displayed temperatures between °F and °C.

## Requirements

### Requirement 1: Generate a summary after the forecast renders

**User Story:** As a user, I want a short written summary of the 5-day forecast, so that I can understand the week's weather without reading each row.

#### Acceptance Criteria

1. WHEN the Weather_App finishes rendering a Forecast, THE Weather_App SHALL display the Summary_Panel below the forecast table.
2. WHEN the Weather_App finishes rendering a Forecast, THE Weather_App SHALL send the city name and the Forecast periods to the Summary_Service.
3. THE Weather_App SHALL render the Forecast before it requests the Summary, so that the Forecast is visible without waiting for the Summary.
4. WHILE the Summary_Service has not yet returned any text, THE Summary_Panel SHALL display the text "Generating summary…".
5. THE Summary SHALL describe the temperature trend, the expected conditions, and the days with precipitation, in no more than 80 words.

### Requirement 2: Stream the summary into the page

**User Story:** As a user, I want the summary to appear as it is written, so that I see results without waiting for the full response.

#### Acceptance Criteria

1. WHEN the Summary_Service receives a valid request, THE Summary_Service SHALL invoke the Model through the Converse_Stream_API.
2. WHEN the Model emits a text chunk, THE Summary_Service SHALL forward the chunk to the Weather_App without waiting for the complete response.
3. WHEN the Weather_App receives a text chunk, THE Weather_App SHALL append the chunk to the Summary_Panel using `textContent`.
4. WHEN the stream ends, THE Weather_App SHALL remove the "Generating summary…" indicator if no text was received and leave the received text in place if any text was received.

### Requirement 3: Keep the forecast working when the summary fails

**User Story:** As a user, I want the forecast to stay usable if the AI summary is unavailable, so that a failure in the optional summary does not block the weather data.

#### Acceptance Criteria

1. IF the Summary_Service returns an HTTP error status, THEN THE Weather_App SHALL display the message "Summary unavailable." in the Summary_Panel and keep the Forecast displayed.
2. IF the request to the Summary_Service does not complete within 30 seconds, THEN THE Weather_App SHALL abort the request and display the message "Summary unavailable." in the Summary_Panel.
3. IF the stream fails after some text was received, THEN THE Weather_App SHALL keep the received text and append the message "Summary interrupted."
4. IF the Bedrock call fails, THEN THE Summary_Service SHALL return an error status and log the error detail on the server without including the detail in the response body.
5. THE Weather_App SHALL display error messages in the Summary_Panel and SHALL NOT display error messages in the existing error display region.

### Requirement 4: Handle city changes and unit toggling

**User Story:** As a user, I want the summary to match the forecast I am looking at, so that I never see a summary for a different city.

#### Acceptance Criteria

1. WHEN the user submits a new city, THE Weather_App SHALL abort any in-progress Summary request and clear the Summary_Panel.
2. WHEN the user activates the Unit_Toggle, THE Weather_App SHALL keep the current Summary text unchanged and SHALL NOT request a new Summary.
3. WHEN the Unit_Toggle re-renders the Forecast, THE Weather_App SHALL keep the Summary_Panel visible below the forecast table.
4. IF a Summary stream from an earlier request delivers text after a newer request has started, THEN THE Weather_App SHALL discard that text.

### Requirement 5: Validate input to the summary service

**User Story:** As the site owner, I want the Summary_Service to accept only well-formed forecast data, so that the endpoint cannot be used to send arbitrary prompts to the Model.

#### Acceptance Criteria

1. THE Summary_Service SHALL accept only the HTTP method POST on `/api/summary`.
2. IF a request body is not valid JSON, THEN THE Summary_Service SHALL return HTTP status 400.
3. IF a request body contains more than 5 periods, THEN THE Summary_Service SHALL return HTTP status 400.
4. IF a request body exceeds 8 KB, THEN THE Summary_Service SHALL return HTTP status 413.
5. THE Summary_Service SHALL build the Model prompt from only these fields of each period: `name`, `temperature`, `shortForecast`, `windSpeed`, and `windDirection`, and from the city name.
6. IF a period field has the wrong type or exceeds 100 characters, THEN THE Summary_Service SHALL return HTTP status 400.
7. THE Summary_Service SHALL pass the period and city values to the Model as data in the user message and keep its instructions in the system prompt.

### Requirement 6: Call Bedrock securely

**User Story:** As the site owner, I want AWS credentials kept off the browser, so that the account cannot be abused through the page.

#### Acceptance Criteria

1. THE Summary_Service SHALL obtain AWS credentials only from the default AWS credential provider chain of the environment in which the Summary_Service starts, and SHALL NOT send credentials to the browser.
2. THE Summary_Service SHALL NOT perform AWS login, prompt for credentials, store credentials, or accept credentials as request data or command-line arguments.
3. IF the default AWS credential provider chain returns no credentials or expired credentials, THEN THE Summary_Service SHALL log a message telling the developer to log in to AWS (for example with `aws sso login`) and restart or retry, and SHALL return HTTP status 503 with a response body that contains no credential or account detail.
4. THE Summary_Service SHALL read the Model identifier and AWS Region from environment variables.
5. THE Summary_Service SHALL set a maximum output token limit of 300 on each Converse_Stream_API call.
6. THE Summary_Service SHALL log one line per request containing the timestamp, method, path, and status, and SHALL NOT log the request body.
7. THE Weather_App SHALL NOT contain AWS credentials, access keys, or Model identifiers.

### Requirement 7: Run locally on localhost:8080

**User Story:** As a developer, I want to log in to AWS myself and then start the whole app with one command, so that I can demo it locally without the app handling my credentials.

#### Acceptance Criteria

1. WHEN the developer runs `start-server.ps1`, THE Weather_App SHALL be served at `http://localhost:8080` and the Summary_Service SHALL be reachable at `http://localhost:8080/api/summary`.
2. THE Weather_App SHALL call the Summary_Service using the relative path `/api/summary`.
3. THE local server CSP and the `<meta>` CSP in `index.html` SHALL list the same `connect-src` sources, and the `connect-src` list SHALL contain `'self'` so that the Weather_App can call `/api/summary`.
4. THE Weather_App SHALL keep `style-src 'self'` and SHALL NOT use `'unsafe-inline'` in any CSP.
5. WHEN the developer has authenticated to AWS in the developer's own terminal (for example with `aws sso login`, by setting `AWS_PROFILE`, or by setting AWS credential environment variables) and then runs `start-server.ps1`, THE `start-server.ps1` script SHALL start the Summary_Service in the environment inherited from that terminal.
6. THE `start-server.ps1` script SHALL NOT perform AWS login, prompt for credentials, store credentials, or accept credentials as arguments.
7. IF the Summary_Service cannot start because Node.js is missing, THEN THE `start-server.ps1` script SHALL print a message naming Node.js as the missing item and continue to serve the static files.
8. IF no AWS credentials are available in the environment of `start-server.ps1`, THEN THE `start-server.ps1` script SHALL print a message telling the developer to log in to AWS first (for example with `aws sso login`) and continue to serve the static files.
9. WHILE AWS credentials are missing or expired, THE Weather_App SHALL display the message "Summary unavailable." in the Summary_Panel and keep the Forecast displayed.

### Requirement 8: Stay compatible with the AWS deployment

**User Story:** As the site owner, I want the summary feature to fit the planned CloudFront deployment, so that deploying it later needs no change to the browser code.

#### Acceptance Criteria

1. THE Weather_App SHALL use the same relative path `/api/summary` locally and on AWS.
2. WHERE the app is deployed to AWS, THE CloudFront distribution SHALL route requests for `/api/*` to the Summary_Service and route all other requests to the S3 origin.
3. WHERE the app is deployed to AWS, THE Summary_Service SHALL run with an IAM role that allows only `bedrock:InvokeModelWithResponseStream` on the configured Model.
4. WHERE the app is deployed to AWS, THE response headers policy CSP SHALL match the local CSP, including `'self'` in `connect-src`.
5. THE aws-deployment spec files (`infra/weather-app.yaml` and `deploy-aws.ipynb`) SHALL be updated in a separate task after the local feature works, and SHALL NOT block the local feature.

### Requirement 9: Basic validation

**User Story:** As a developer, I want a minimal check that the code is valid, so that I can trust it without a test framework.

#### Acceptance Criteria

1. WHEN `node --check` is run on `weather.js` and on the Summary_Service source file, THE command SHALL exit with status 0.
2. THE project SHALL include no test framework and no test infrastructure beyond `node --check` and the existing test scripts.
